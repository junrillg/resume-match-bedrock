# AWS deployment reference

The local service journey is executable; this AWS topology is defined and mock-plan verified, not deployed. [The service journey](../../docs/aws-service-journey.md) explains what each resource does. This root targets the commercial AWS partition. It defines the same durable SSE delivery path with small initial Fargate counts, private encrypted Valkey shards and a bounded database proxy. Account-specific deployment and capacity remain unverified; no AWS resources are created by the local checks.

## Review prerequisites

Choose the account/region, three standard AZs, supported PostgreSQL17 minor/instance class, RabbitMQ4.3 mq.m7g capacity, GuardDuty Malware Protection for S3 availability and Bedrock model/profile availability. Confirm model access and exact resource ARNs (include underlying foundation models for inference profiles). Confirm the selected provider output matches the application evidence contract. The existing delegated public Route53 zone must contain the chosen hostname. The deploying role needs scoped Terraform provisioning permissions and permission to create AWS service-linked roles/grants. Supply existing SNS alarm destinations if notifications are needed; without them alarms remain visible in CloudWatch but send no notifications. The deploying identity also needs GuardDuty plan management and scoped iam:PassRole to malware-protection-plan.guardduty.amazonaws.com. No broad GuardDuty detector is provisioned by this root.

Bootstrap remote state separately: existing private encrypted versioned S3 bucket, state KMS key, TLS-only bucket policy and least-privilege operator/automation access. Terraform state, local caches and saved plans contain generated application/broker/reviewer credentials. Use S3 native lockfile and encryption; never upload plans/state into GitHub or place AWS keys in tfvars. The state bucket is an account prerequisite, not the application's document store. Backend IAM must permit state Get/Put, lockfile Get/Put/Delete and KMS as appropriate. Use short-lived authorized AWS identity; do not copy credentials into files or CLI arguments.

## Deploy in three reviewed phases

```mermaid
flowchart LR
  A["Foundation<br/>Repositories + secrets + network"] --> B["Release<br/>Real image digests + zero replicas"] --> C["One-off database bootstrap<br/>Verify exit code + safe log"] --> D["Enable services<br/>Verify HTTPS endpoint"]
```

These are operator release stages, not AWS service icons or request-processing hops.

1. Copy backend.hcl.example to a private ignored backend.hcl; copy terraform.tfvars.example to ignored terraform.tfvars and replace every illustrative value. Keep image_digests=null, enable_services=false and bootstrap_completed=false. Initialize the protected backend, review a saved plan privately, approve and apply it. This creates foundation, repositories and secrets, with no fake image/task placeholders. The HTTPS endpoint has no healthy application yet.
2. Build backend and web images for linux/amd64 from repository root, scan and publish to the output ECR repositories under immutable release tags. Use normal ECR login via stdin in your own terminal. Capture each actual digest; fill image_digests with sha256 values. Review/apply a second plan: task definitions and services are created with desired_count=0. The task definitions use immutable ECR images, private networking, injected secrets, verified RDS/MQ TLS and co-located nginx/API, independent ASGI gateway/event-relay roles and a proxy with separate application/stream identities. Terraform does not build images, execute SQL or run ECS tasks.
3. In your operator terminal save `terraform output -json bootstrap_network > bootstrap-network.json` (ignored) and run `aws ecs run-task --region <chosen-region> --cluster <cluster_name-output> --task-definition <bootstrap_task_definition-output> --launch-type FARGATE --platform-version 1.4.0 --network-configuration file://bootstrap-network.json --query 'tasks[].taskArn' --output text`. Inspect the result for a started task, wait for it to stop, then query only `tasks[].containers[].{name:name,exitCode:exitCode,reason:reason}` using describe-tasks. Require exit code 0 and the metadata-only success log before proceeding. A failed run may leave some migrations applied; repair privately then rerun. Do not enable services on failure. Run bootstrap on one task at a time.

Bootstrap connects directly to RDS and receives its managed master password, application/stream passwords and bootstrap-only reviewer password through ECS secret injection. It rejects elevated existing roles/memberships, creates a nonlogin migration owner, and migrates through a temporary in-memory direct bootstrap connection. Runtime `resume_app` receives schema usage, table DML and sequence usage; it cannot create, alter or drop schema objects or assume the owner role. An existing app-owned schema is transferred through the guarded ownership transition. A nonstaff reviewer is created only if absent; adopted passwords are preserved.

The stream login has SELECT on only the four authentication/replay tables, read-only transactions, UTC and finite statement/lock timeouts. Ordinary roles connect through RDS Proxy; gateway and app credentials remain separate. Proxy clients verify the Amazon Trust Services chain; direct bootstrap verifies the RDS chain. Normal execution roles cannot read master/reviewer secrets. No password is printed or passed in task command arguments.

Confirm document_scan_plan reports ACTIVE, bucket EventBridge notifications are enabled, and GuardDuty can scan/tag a synthetic original before enabling admission. WARNING/ERROR plans block service enablement; ACTIVE alone does not prove a particular object has been scanned. Set bootstrap_completed=true and enable_services=true only after successful bootstrap and verify the proxy target is available with both scoped identities. Review/apply starts the small profile below, including three gateways and one event relay; the autoscaler uses the same configured limits. Each deployment uses circuit-breaker rollback; database schema migrations still require a separate reviewed one-off task before compatible service rollout. Retrieve the initial reviewer password privately through authorized SecretsManager access in your own console; never paste it into a ticket, shell command or tool transcript.

## Verify the actual endpoint

Open application_url over HTTPS, sign in as the chosen reviewer, submit a synthetic PDF/TXT or pasted text and weighted requirements, observe receipt, scan-pending/queued/running state and persisted report. Verify a new object cannot be read before its clean scan tag, and application roles cannot forge or remove the scanner tag. Download the authorized original byte-for-byte, reuse it for another comparison, and reprocess from the retained source. Exercise owner denial and deletion/expiry recovery against synthetic records before any real documents. Record job/admission request IDs. Use the saved CloudWatch query (filter by the admission UUID) to connect API acceptance, relay confirmation, worker/provider events and final save. Confirm `/api/events/` reaches the independent async gateway, live changes trigger only authorized affected-resource reads, and reconnect recovers durable notices without automatic HTTP polling. REST reads have their own request UUIDs. Review stream target health, ECS tasks, MQ backlog, database/proxy metrics, Valkey shards and delivery-age alarms. Validate duplicate submissions, provider failure/recovery and managed-service failover only after a deliberate account/cost test plan. Logs omit resume bodies, filenames, usernames, model payloads and credentials. Model output is still validated against the uploaded source before deterministic scoring.

## Event delivery and configured capacity

A visible change commits its owner revision with the business transaction. The event relay publishes to the same ordered Valkey primary endpoints used by every gateway; `owner_id % shard_count` selects an independent group. Valkey is disposable live delivery, while PostgreSQL owns replay and the inbox. Changing the shard order/count requires a coordinated publication pause and gateway drain, followed by durable reconciliation.

The exact HTTPS path `/api/events/` routes to gateway port8001; ordinary requests use nginx/API port8080. Gateways use a bounded read-only database identity through RDS Proxy. API/worker/relays use the separate app identity through that same proxy; bootstrap alone bypasses it. Neither delivery role can access originals, invoke Bedrock or read broker/master credentials.

| Service | Initial / maximum tasks |
| --- | --- |
| App / worker | 2 / 12 each |
| Job relay / event relay | 1 / 1 each |
| ASGI gateway | 3 / 12 |

`service_capacity` changes those finite limits. Gateway connection target tracking uses emitted `ConnectedStreams` averages; CPU/memory policies provide independent safeguards. `enable_services=false` sets scaling bounds to zero, including previously autoscaled services. Missing-metric alarms have actions suspended while services are intentionally off. Alarms are operating signals, not evidence of a measured SLO.

Small-profile admission defaults are **2 logical jobs/s**, **32 active jobs**, **2 active jobs/owner** and a proposed **60s observed queue-age gate**; stale relay health also stops new admission. This threshold is not a promise that every accepted job starts within 60 seconds. Same-key retries recover accepted work without another charge. Raise these inputs alongside worker/model supply. The planning peak is 100 comparisons/s, independent of concurrent connections; this small profile does not claim to sustain it. Service time, burst duration, model quotas and latency objectives remain operating inputs.

For this admission-reservation migration, pause admission and drain/stop old workers and the job relay before migrating, then start the new roles. Bounded repair reconciles terminal reservations left by an old worker; it does not make arbitrary mixed-version deletions safe. Preserve accepted jobs and source volumes throughout the coordinated cutover.

One million simultaneous users is a growth scenario on this same path, not the initial desired count or a required cloud load test. For example, proposed2000 connections/process at70% utilization and discrete one-AZ-loss headroom needs1074 balanced planning replicas. A200% rollout would register2148 gateway targets before API targets, exceeding published default1000-target quotas. `capacity_limits` checks configured target/CPU/client/backend/address ceilings, not actual account quota approval. Large settings require matching verified deployment budgets and measurements; small plans do not require provisioning that envelope. Current lifetime/reconnect settings also create substantial full-reconciliation traffic during fleet rollover; connected-user arithmetic alone does not size the API/database.

Three private /20 subnets reserve room for the configured maximum, rolling overlap and one-AZ-loss placement; public /24s do not overlap. Existing deployed subnet CIDRs must be migrated deliberately rather than replaced without review. RDS Proxy pooling does not establish unlimited PostgreSQL supply or eliminate SQL/session pinning; retain role/client budgets, monitor borrow latency/pinning, and measure the selected instance/model before changing admission.

## Document storage and malware gate

The API stores exact originals at generated `originals/<document UUID>` keys; PostgreSQL owns the owner, checksum, lifecycle and results. The API role can upload and read/tag-check; the worker can read/tag-check; the relay can delete. Reads require `GuardDutyMalwareScanStatus=NO_THREATS_FOUND` in the bucket policy as well as application authorization and checksum validation. Only the scanner can change object tags. Upload-time scan-tag forgery is denied. Generated keys and stored checksums protect the application workflow; this is not WORM storage or an IAM guarantee against replacement by a compromised uploader role.

Uploads rely on bucket-default SSE-KMS with the selected key; explicit alternate algorithms/keys are denied. S3 Bucket Keys are off so KMS policies can restrict requests to original-object encryption context; the scanner additionally needs the validation-object context. No KMS endpoint is required for these S3-mediated encryption operations. No document or storage key is passed to the broker or logged by the application.

Cloud tasks receive `DOCUMENT_BUCKET`, `DOCUMENT_REGION`, `DOCUMENT_SCAN_MODE=guardduty` and `DOCUMENT_RETENTION_DAYS`; they use ECS task credentials. Local object endpoints and access/secret keys are absent. The scanner plan protects `originals/`, enables object tagging, and uses the documented service role for bucket notifications, managed EventBridge rules, object reads/tags and its validation object. It scans newly uploaded objects; old/pre-existing objects are not assumed clean.

Missing scan tags keep processing pending for the application's bounded ten-minute scan window without consuming provider attempts. `THREATS_FOUND`, `UNSUPPORTED`, `ACCESS_DENIED` and `FAILED` fail closed; unavailable scan/tag access cannot reach parsing, model use or download. GuardDuty tagging/size/type limitations and service delay still apply. A clean scan reduces risk; it is not proof a file is harmless. ClamAV runs locally and does not establish AWS scanner parity. Source/mock-plan verification does not establish real IAM enforcement, scan behavior or deployment readiness; record those account-specific checks after deployment.

## Operating limits and cleanup

Costs include three MQ nodes, multi-AZ RDS/storage/backups, five interface endpoint types across three AZs, ALB, ECR, CloudWatch/ContainerInsights, SecretsManager/KMS, two multi-AZ Valkey replication groups, RDS Proxy, Fargate replicas, original-object storage/requests, GuardDuty scans and scan-result tagging, and Bedrock usage. No NAT is needed: the S3 gateway preserves regional ECR layer reads and separately permits only app/worker/relay document operations. GuardDuty manages its EventBridge scan rule outside application subnets; it does not add another application work queue. Valkey is live wake transport and finite owner-connection leases; PostgreSQL retains events/results. No CloudFront/API Gateway/Kafka/StepFunctions are implied. CloudWatch lifecycle logs are best effort/nonblocking with 30-day retention; alarms detect failures/backlog/storage and target health, but do not establish an SLO. The SDK has bounded retries and worker job budgets; provider calls may repeat while the database permits one committed report.

Application/broker passwords are generated once by Terraform and retained in protected state. Rotate through a reviewed coordinated update: pause affected tasks, change database/broker credentials and matching SecretsManager version, rerun migrations/bootstrap where appropriate and redeploy; changing an MQ user block alone is not a supported RabbitMQ password rotation workflow. RDS rotates its managed master secret independently. Originals, extracted text and associated comparisons/results use the confirmed configurable project policy of 90 days. Owner deletion can run earlier; application expiry immediately denies access and the relay reconciles physical and relational deletion. S3 lifecycle expiration is an asynchronous backstop, not an exact deletion deadline or replacement for database cleanup. Rejected/abandoned uploads use application cleanup. After restoring a database backup, run expiry/deletion reconciliation before reopening admission; the seven-day RDS backup window can retain data after live deletion. Confirm the policy fits the actual workload before using real applicant data.

The originals bucket has force_destroy=false and Terraform prevent_destroy; a destroy or bucket replacement is intentionally blocked until a separate reviewed preservation/erasure change. It is newly created without enabled versioning (Suspended), with no replication or object-lock claim; changing versioning/backup policy requires explicit historical-version erasure rules. Keep the KMS key while any retained objects, snapshots or logs require it. Deletion protection defaults on for RDS/ALB. First stop admission and set services off; export required reports and verify backups. Review deletion protection changes separately before destroy. RDS always takes a final snapshot (set final_snapshot_identifier to an unused name if an older snapshot has the same name); log groups are retained with skip_destroy and SecretsManager uses 30-day recovery. ECR repositories refuse deletion while images remain. Preserve the state bucket, snapshots/logs and KMS key as long as any retained encrypted data is needed; Terraform schedules key deletion only after 30 days, and an indiscriminate destroy would make retained data unreadable. Remove image tags and retained resources only under a separate data-preservation decision.
